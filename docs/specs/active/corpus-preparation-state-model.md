# Sibyl Corpus Preparation Platform v2 — Persistent Processing State Model Specification

## Status

Active specification.

This document defines the intended change to the corpus preparation workflow. It describes required behavior, contracts, and validation rules.

It is not a replacement for implementation documentation. After implementation, stable architectural knowledge must be moved into owning documentation.

## Purpose

The corpus preparation pipeline must support reliable incremental processing of a growing literary corpus.

The system must preserve progress across executions, avoid unnecessary repeated processing, recover safely after interruptions, isolate failures between independent works, provide deterministic rebuild behavior, and keep persistent state separate from generated artifacts.

## Design principles

### Persistent objects, not jobs

Processing state represents the current condition of persistent corpus objects. It is not a queue of commands.

The next action is derived from:

- current state;
- available artifacts;
- fingerprints;
- dependency availability;
- validation results.

### Idempotent execution

Repeated execution of the same command must not duplicate work or corrupt state.

## Stable work identity

Each literary work has a stable `work-id`.

`work-id` is created in the reviewed work catalog and is not generated by processing scripts.

Example:

```yaml
works:
  - id: tolstoy-anna-karenina
    author: leo-tolstoy
    title: Anna Karenina
```

The identifier remains unchanged after rebuilding, changing processing configuration, adding translations, or changing runtime corpus composition.

## State hierarchy

The system uses two state levels.

### Global processing index

Location:

```text
state/index.yaml
```

Purpose:

- fast discovery;
- CLI status;
- high-level scheduling decisions.

### Per-work processing state

Location:

```text
data/work/<work-id>/state.yaml
```

Contains:

- stage states;
- fingerprints;
- blockers;
- retry information;
- short errors;
- artifact references;
- validation results.

The global index is a summary. Detailed work state remains local.

## Stage lifecycle

Allowed stage states:

```text
pending
running
completed
failed
retryable
blocked
skipped
```

A completed stage may only be invalidated by a relevant fingerprint change.

## Fingerprints

The system must distinguish:

- source identity;
- canonical text identity;
- processing configuration identity;
- generated artifact identity.

Previous results may be reused only when required fingerprints match.

## Resume behavior

`advance` must continue from persistent state instead of rescanning every processed work.

Required flow:

```text
read state/index.yaml
    ↓
select pending, stale, retryable works
    ↓
load detailed state
    ↓
continue processing
```

## Crash recovery

Interrupted stages must be detected.

Example:

```yaml
canonical:
  status: running
```

Without an active execution lock, the next run resolves the interruption as retryable or failed.

Large diagnostics belong in logs. State stores short references only.

## Execution locking

Only one corpus orchestration process may modify processing state at a time.

Lock location:

```text
corpus-builder/.sibyl-corpus.lock
```

The lock is created using atomic exclusive creation.

Required commands:

```bash
sibyl-corpus lock-status
sibyl-corpus unlock
```

Stale locks require explicit verification before removal.

## Atomic publication

The required order is:

```text
temporary artifacts
    ↓
validation
    ↓
artifact publication
    ↓
state update
```

State must never claim successful artifacts before publication succeeds.

## Failure isolation

A failed work must not stop unrelated works.

The final execution summary must report all outcomes.

## Prepared work compatibility

The state model must support reusable prepared work artifacts:

```text
source work
    ↓
prepared work artifact
    ↓
runtime corpus assembly
```

Expensive preparation must not be repeated when inputs are unchanged.

## Validation requirements

Tests must verify:

- stable work-id handling;
- workspace creation;
- resume behavior;
- fingerprint invalidation;
- state consistency;
- lock exclusivity;
- stale lock handling;
- failure isolation;
- deterministic repeated execution.

## Completion criteria

The feature is complete when:

- interrupted executions can recover;
- completed works are not unnecessarily rebuilt;
- failures remain isolated;
- state and artifacts remain consistent;
- concurrent mutation is prevented;
- validation covers persistent state contracts.
